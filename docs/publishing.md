# 매일 발행 운영

## 실행 위치와 시간

Codex의 `보안 노트 매일 발행` 예약은 한국 시간 매일 18:30에 실행한다. 주말에도 같은 시각을 사용한다. 로컬 파일을 사용하는 현재 예약은 개인 PC와 Codex 앱이 실행 중이어야 한다.

GitHub Actions의 `매일 보안 글 작성 및 발행` 워크플로도 매일 한국 시간 18:30(UTC 09:30)으로 구성했다. GitHub 호스팅 실행기를 사용하므로 활성화 후에는 개인 PC나 Codex 앱을 켜 둘 필요가 없다. 이 시각은 시작 예정 시각이며 GitHub 대기열·원문 조회·검증 시간에 따라 공개가 늦어지거나 실행이 누락될 수 있다. 발행 계획도 평일 18시 이전에는 새 글을 요청하지 않으며 preview는 이 제한을 적용하지 않는다.

현재 `DAILY_PUBLISH_ENABLED`는 활성화하지 않았다. OpenAI Platform의 OAuth 연결 오류로 키를 생성하지 못했으며 `OPENAI_API_KEY` Secret도 미등록이다. 키 등록과 `preview` 검증을 마친 뒤 변수를 `true`로 바꾸고 기존 Codex 로컬 예약을 중지한다. 설정 파일이 있다는 사실만으로 무인 생성·발행이 검증된 것은 아니다.

## 주제와 날짜

- 주통기는 2026 KISA 공식 원문의 U-01~U-67을 순서대로 다룬다. 항목명·중요도·페이지는 scripts/unix-2026-topics.json에 원문 파일 해시와 함께 보관한다. 다음 번호는 실제 공개 글과 초안에서 계산한다. 2026-10-17 검토 시점에는 U-12까지 공개돼 있다.
- 원문 PDF를 HTTPS로 다운로드해 SHA-256을 대조하고 다음 항목의 본문을 추출한다. 파일이나 기준이 달라지면 검토 전까지 주통기를 보류한다. U-67 이후 번호는 생성하지 않는다. 이후에는 Qualys만 계속할 수 있다.
- Qualys는 기존 글과 초안을 읽고 docs.qualys.com에서 해당 제품의 공식 문서를 확인한다. 태그·범위·Search List·Option Profile·QID·보고서 해석 등에서 새 주제를 고른다. 기존 제목과 본문이 크게 겹치는 글은 거부한다. 의미상 중복을 완전히 판별하는 검사는 아니다.
- 기본 두 종류는 각각 하루 최대 1편이다. 수·토요일에만 웹·인프라 보안 실습을 추가로 한 편 검토한다. 추가 글은 한국 시간 월~일에 최대 두 편이며 같은 주의 초안과 수동 글도 센다. 두 분야 중 최근 글이 오래된 쪽을 우선 요청한다. 적절한 주제나 공식 근거가 없으면 보류하고 최대 세 편을 채우려고 작성하지 않는다.
- 날짜는 Asia/Seoul로 계산한다. 오늘 같은 종류의 글이나 초안이 있으면 새로 만들지 않는다. 놓친 날짜를 소급해 채우지 않는다. 다음 번호에 기존 초안이 있으면 넘기지 않고 보류한다.

## 작성·검증·발행 경계

1. 계획 단계는 기준 main SHA, 한국 날짜, 기존 글과 다음 번호를 고정한다. 공식 PDF가 확인되지 않으면 Qualys만 독립적으로 진행할 수 있다.
2. 작성 단계는 고정한 공식 Codex Action과 CLI를 사용한다. 저장소 권한은 contents:read, Codex 프로필은 :read-only, safety-strategy는 drop-sudo다. 모델은 CLI 기본값이며 요청 시간은 작업당 최대 25분이다. API 키는 이 단계의 공식 Action에만 전달한다. API 요금은 별도로 발생한다. 시간 제한은 비용 상한이 아니므로 OpenAI 프로젝트의 사용량·한도도 관리해야 한다.
3. 생성 결과는 제한된 JSON으로 받는다. 파일 경로, 날짜, 카테고리, 시리즈 번호, 참고 자료 절은 신뢰하는 코드가 만든다. 원문 근거·태그·본문 구성·마크업·중복·비밀 값 형태를 검사한다. 임의 파일 수정·기존 글 덮어쓰기·외부 이미지·본문 HTML·임의 링크는 허용하지 않는다. 출처 링크는 문서 제목을 쓰며 확인일은 관리용 sourcesChecked에 보관한다. 본문에 확인일과 일괄 면책 문단을 덧붙이지 않는다.
4. 각 글은 공식 문서 두 개 이상과 짧은 대조용 근거를 제출한다. 허용한 HTTPS 공식 호스트만 요청하고 리디렉션도 다시 검사한다. 문서에 근거 문구가 실제 존재하는지 확인하지만, 모든 문장의 의미와 사실관계를 자동으로 증명하는 것은 아니다.
5. Python 예제는 다른 작업의 Docker 컨테이너에서 실행한다. 네트워크 없음, 읽기 전용 루트, 권한 제거, 비특권 사용자, PID·메모리·CPU·시간·출력 제한을 적용한다. 코드 파일만 읽기 전용으로 넣으며 API 키·GitHub 토큰·저장소를 넘기지 않는다. 실제 제품·API·원격 스캔·운영 계정 변경은 허용하지 않는다.
6. 정상 종료한 실제 stdout·stderr·환경·날짜·코드 해시를 기록한다. 실행 기록을 작성 모델이 만들게 하지 않는다. 설명 도식은 기존 SVG 생성기로 만든다. 본문에서 관계를 설명하는 곳에 `[[diagram]]`, 코드 뒤 결과를 해석하는 곳에 `[[run:1]]` 또는 `[[run:1:fold]]`를 넣는다. 자료 앞뒤에 설명을 두고 시작·끝에 몰아 붙이지 않는다. 누락·중복·순서 오류는 발행 전에 거부한다. 표·목록의 사용과 자료 순서는 글의 내용에 맞춰 바꾼다. 기존 글의 실행 날짜·환경·출력은 보존한다. 세부 기준은 [본문 자료 배치](article-media.md)를 따른다.
7. `npm run check`, `npm test`, `npm run build`, `npm run verify`와 1440·390·320px Chromium 검사를 통과해야 한다. 글·목차·도식·실행 출력·가로 넘침·콘솔 오류를 확인한다. 본문·근거·예제 실행 검증에서는 실패한 글만 보류할 수 있다. 사이트 공통 검사나 화면 검사가 실패하면 그날 발행을 중단한다. 모두 보류되면 작업을 실패로 끝낸다.
8. 별도의 contents:write 작업이 검증된 결과만 다시 구성한다. 계획 SHA와 원격 main이 달라졌으면 중단한다. 새 글·새 SVG·지정된 데이터 파일만 일반 커밋·푸시하며 강제 푸시와 이력 변경은 하지 않는다.
9. GITHUB_TOKEN으로 한 푸시는 일반 push 워크플로를 다시 실행하지 않으므로, 발행한 SHA를 기존 Pages 워크플로에 명시적으로 전달한다. 배포 직전 최신 main도 대조한다. 배포 후 글·그림 원본 해시·실행 기록·검색·RSS를 확인한다. 새 글이 이미 커밋된 상태에서 배포만 실패하면 publish를 다시 실행해 중복 작성 없이 재배포할 수 있다.

생성·계획·검증 JSON과 브라우저 캡처는 GitHub Actions 아티팩트에 1일 보관한다. 공개 저장소 아티팩트에도 접근할 수 있으므로 가상 자료만 사용한다. API 키와 로컬 비밀 파일은 아티팩트·커밋에 포함하지 않는다. 워크플로 실패는 GitHub Actions 기록에서 확인하며 별도 이메일·메신저 전송은 구성하지 않는다.

## 수동 실행

GitHub 저장소의 Actions에서 이 워크플로를 선택하고 `Run workflow`로 실행한다.

| 모드 | 동작 | API 사용·저장소 변경 |
| --- | --- | --- |
| verify | 공식 PDF 대조, Docker 격리, 기존 사이트 회귀·화면 확인 | API 없음, 커밋 없음 |
| preview | 다음 주제 작성과 전체 검증, 결과 아티팩트 보관 | API 사용, 커밋·배포 없음 |
| publish | 오늘 누락된 종류만 작성·검증·커밋·배포 | API 사용 가능, 활성 변수 필요 |

preview는 같은 날 글이 있어도 다음 주제로 실제 생성 경로를 검사한다. 발행 코드가 preview 결과를 커밋하지 못하도록 모드를 다시 확인한다. publish에서 오늘 요청할 종류가 모두 준비됐으면 생성 API를 호출하지 않고 현재 main 배포를 재확인한다.

## 중지와 복구

`DAILY_PUBLISH_ENABLED=false`로 새 클라우드 발행을 중지한다. 키 만료·비용·원문 변경·권한 오류는 근거를 확인한 뒤 복구한다. 발행한 글에 문제가 있으면 해당 글과 연결 기록을 검토해 일반 수정 커밋으로 고친다. 키가 노출되었다면 Platform에서 폐기·재발급하고 Secret을 교체한다. 키 값은 채팅이나 로그로 전달하지 않는다.

자동 검사는 형식·실행·문서 근거와 공개 반영을 다루며 전문가의 문장별 검토를 대신하지 않는다. 제품 문서 변경, 모델 기본값·비용 변화, 의도와 다른 코드 설명, 의미상 중복은 지속적인 품질 검토가 필요하다. 공식 기준이나 실행 근거가 부족한 글은 수량을 채우려고 발행하지 않는다.
