# 콘텐츠와 작성 기준

보안 설정을 읽고, 작은 실습으로 확인하고, 판단의 근거를 남긴다. 한국어를 중심으로 쓰되 명령·필드·제품 이름은 정확하게 유지한다.

공개 글은 src/content/posts/에서 관리한다. 시리즈 범위와 글 수는 실제 콘텐츠에서 계산한다. 메인은 최근 8편, 전체 글 목록은 페이지당 12편을 보여 준다. 공개 카테고리는 주통기·Unix·애플리케이션 보안·인프라 보안·Qualys·코딩 테스트다. 내용 없는 카테고리를 미리 노출하거나 글 수를 채우려고 예제 글을 공개하지 않는다.

## 카테고리와 점검 대상

| 카테고리 | 분류 기준 | 분류 예 |
| --- | --- | --- |
| 주통기 (`critical-infrastructure`) | 공식 점검 가이드의 항목 번호와 판단 기준을 설명하는 글 | U-01~U-12 |
| Unix (`unix`) | 특정 점검 항목에 속하지 않는 Unix·Linux 동작과 설정 | umask와 파일 권한 |
| 애플리케이션 보안 (`application-security`) | 인증·접근 제어와 안전한 입력·파일 처리 | CORS, 다운로드 경로, gzip 출력 제한 |
| 인프라 보안 (`infrastructure`) | 시스템·네트워크 보안 설정과 통신 검증 | TLS 버전과 인증서 검증 |
| Qualys (`qualys`) | Qualys 제품 기능과 공식 문서 해설 | 인증 스캔, 자산 태그, Search List 등 |
| 코딩 테스트 (`coding-test`) | 입출력·자료구조·복잡도·경계값 검증을 중심으로 한 문제 풀이 | CIDR 조회, 로그인 실패 집계 |

보안 용어가 등장한다는 이유만으로 문제 풀이를 인프라 보안에 넣지 않는다. gzip 출력 제한처럼 HTTP에 한정되지 않는 입력 처리 보안은 애플리케이션 보안으로 분류한다. 글의 주된 목적을 기준으로 카테고리를 정하고 세부 기술은 태그로 표시한다.

주통기에는 `assessmentTarget`을 필수로 지정한다. 현재 대상은 `unix`이며 일반 Unix 글에는 이 필드를 쓰지 않는다. 카테고리와 대상은 `src/lib/taxonomy.mjs`에서 관리한다. Windows·DBMS 등 다른 대상의 첫 글을 추가할 때 대상 ID·표시 이름을 등록하면 대상별 목록과 링크가 생성된다. 글이 없는 대상은 메뉴·페이지·사이트맵에 노출하지 않는다. 새 연도·대상의 번호순 시리즈를 만들 때는 같은 파일의 시리즈·번호 범위와 해당 시리즈 페이지를 공식 가이드에 맞춰 추가한다.

주통기 Unix의 기존 `series: unix-2026`, 항목 번호, 글 주소와 번호순 목차는 유지한다. 기존 `/categories/web/` 주소는 애플리케이션 보안으로 이동한다. 발행일·본문·코드·실행 기록은 카테고리 편집과 분리해 보존하며 `content-baseline.json`의 과거 분류도 최초 검증 시점의 기록으로 남긴다.

## 글의 구성

도입은 글의 내용에 맞춰 고른다. 정의가 필요한 글은 개념에서, 실습 글은 실제 출력이나 재현할 조건에서, 문제 풀이 글은 입력과 제약에서 시작할 수 있다. 모든 글을 가상의 장애 상황이나 질문으로 시작하지 않는다. 설정값·명령·관찰·해석의 순서도 설명에 맞게 정하며 목차를 채우기 위한 절은 만들지 않는다.

제목에는 실제 문제나 설정 이름을 쓴다. '읽고, 확인하고, 기록합니다', '근거를 연결한다', '구조로 읽기' 같은 표어와 추상적인 결론을 쓰지 않는다. 모든 글의 문단 수와 도입·마무리를 같은 틀에 맞추지 않는다. 전문성은 긴 용어와 면책 문구보다 정확한 조건, 명령, 출력, 해석에서 드러나도록 쓴다.

초안을 쓴 뒤 최근 글 세 편과 도입, 소제목 순서, 마지막 문단을 대조한다. '설정했다고 끝나는 것은 아니다', '이것만으로 판단할 수 없다' 같은 대비 구조가 이어지면 긍정형으로 동작 조건과 필요한 자료를 직접 설명한다. '확인한다'를 동의어로만 바꾸지 말고 무엇을 조회·비교·시험하는지 적는다. '검증은 성공했지만 운영 판정은 아니다' 같은 한계 설명은 관련 예제 옆에서 한 번 설명하고 기술적 의미가 달라지는 경우에만 다시 쓴다.

마지막 문단에서 글 전체를 다시 요약하거나 '중요하다', '도움이 된다'로 끝내지 않는다. 독자가 수행할 구체적인 작업이 있으면 적고 설명이 끝났으면 그대로 마친다. 자연스러운 문체를 위해 경험담·담당자 발언·제품 사용 이력을 만들어 넣지 않는다. 실제로 수행한 실험은 기록으로 뒷받침하고 가정은 조건문이나 예시라고 밝혀 쓴다.

엠 대시(U+2014)는 사용하지 않는다. 설명은 문장으로 잇고, 참고 자료 제목이나 짧은 부연에는 콜론·괄호·쉼표를 문맥에 맞게 쓴다. 그림 문구와 예제의 출력 문구에도 적용한다. 외부 도구의 실제 출력은 임의로 바꾸지 않는다. 예제의 출력 문구를 고쳤다면 다시 실행한 결과와 코드 해시를 기록한다.

실행 가능한 코드는 격리된 환경에서 확인하고 출력과 종료 코드를 기록한다. 실행하지 못하면 이유와 범위를 적으며 예상 출력을 실제 결과처럼 표시하지 않는다. 기존 코드의 기준 정보는 content-baseline.json에 보관한다. 코드를 의도적으로 바꿀 때는 재검증 후 기준 정보도 함께 검토한다.

각 글에 설명 도식을 제공하고 필요한 곳에 사진·캡처를 추가한다. 사진 형태의 생성 이미지는 캡션에 생성 사실을 표시하며 제품 실행이나 개인 경험의 증거로 사용하지 않는다.

도식은 설명할 관계에 맞춰 흐름·비교·분기·시간축·순환·연결 구조·구간 등으로 고른다. 최근 글과 그림 모양을 다르게 만들려고 의미 없는 화살표나 임의의 수치를 넣지 않는다. 시점은 시간축, 판단은 분기, 실제 범위의 겹침은 구간 그림으로 표현하고, 수치 근거가 없는 내용은 정량 차트로 꾸미지 않는다. 형식별 입력과 예시는 [이미지·실행 기록 기준](article-media.md)을 따른다.

그림 안에 전체 제목·브랜드·하단 설명을 반복하지 않는다. 노드의 조건과 수치는 유지하고, 캡션은 축·화살표의 뜻이나 예제 범위를 보충한다. 제목은 대체 텍스트와 메타데이터로 보존하며 필요한 설명을 메타데이터에만 숨기지 않는다. 본문·그림·캡션을 함께 읽어 중복 문장을 덜어 낸다.

자료의 위치도 설명 흐름에 맞춘다. 관계를 설명한 문단 옆에는 도식을, 설정 차이를 비교할 때는 표를, 실습 코드 뒤에는 실제 출력과 해석을 둔다. 같은 내용을 표와 원본 로그로 반복한다면 로그는 접어 제공한다. 문서 해설만 있는 글에 실행 기록을 만들어 붙이거나 모든 글의 도입에 그림부터 놓지 않는다. 긴 코드는 원문을 보존한 채 접어 읽을 수 있게 한다. 표식과 배치 검증 방법은 [이미지·실행 기록 기준](article-media.md)을 따른다.

## 근거와 공개 범위

주통기는 해당 연도의 KISA 공식 가이드에서 번호·제목·양호/취약 기준·운영체제 범위를 확인한다. 제품 기능은 Qualys 공식 문서를 기준으로 버전·구독·권한 조건을 확인한다. 가이드 문구를 길게 복제하지 않고 직접 정리한다. 본문 끝에는 제목이 있는 출처 링크를 둔다. 확인일은 frontmatter의 sourcesChecked에 보관하며 본문·참고 자료 제목에는 표시하지 않는다.

'실제 구독·제품 버전·사용자 권한 또는 스캔 결과를 확인한 기록은 아니다' 같은 문장을 글마다 붙이지 않는다. 제품이나 예제의 한계가 독자의 판단을 바꿀 때 해당 설명 옆에 짧게 적는다. 실행 날짜·환경·종료 코드 등 실측 기록은 유지한다.

문체 편집과 사실 변경을 구분한다. 문장을 줄여도 기준값·적용 조건·버전·구독·권한 차이·예외·실습 범위는 보존한다. 코드·출력·출처 링크·발행일을 편집 전후로 대조한다. 기술적 조건이나 예제 코드를 바꿔야 한다면 문체 수정에 섞지 않고 공식 근거와 재실행 결과를 검토한다. 반복 단어의 빈도만으로 문체 품질이나 작성 주체를 판정하지 않는다.

실제 운영 계정, 비밀번호·키·쿠키, 내부 환경과 원본 로그는 수집하거나 게시하지 않는다. 실습은 가상 파일과 루프백을 우선한다. 문서 해설과 직접 실행한 관찰을 구분하고, 제품 운영 경험이나 개인 역할을 꾸며 쓰지 않는다.

## 매일 발행

한국 시간 매일 18:30에 주통기 다음 항목과 기존 글과 겹치지 않는 Qualys 주제를 각각 최대 1편 검토한다. 주말도 같은 시각으로 운영한다. 수·토요일에는 추가 애플리케이션·인프라 보안 실습 1편을 검토할 수 있다. 추가 글은 초안과 수동 글을 포함해 월~일 기준 주 2편 이내, 전체는 하루 최대 3편이다. 설명할 새 문제가 없거나 근거·실행 검증이 부족하면 발행하지 않는다. 수량을 채우는 요약·재작성·제품 소개는 만들지 않는다.

추가 주제는 파일·입력 검증, HTTP, TLS, 로그 분석, 설정 비교 등 구체적으로 실습할 수 있는 내용을 고른다. 주요 시리즈는 번호순으로 이어 가며 소급해서 여러 날 분량을 발행하지 않는다. 중복 실행·재시도도 같은 글을 만들지 않는다. 상세 절차는 [발행 운영](publishing.md)을 따른다. 기존 글의 삭제·비공개 전환은 가치·중복·연결 관계를 먼저 검토하고 별도로 기록한다.
