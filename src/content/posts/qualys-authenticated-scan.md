VM/VMDR의 Authentication Report는 대상 호스트의 인증 상태를 보여 줘요. `Passed`는 로그인 성공을 뜻하지만 이후 파일·레지스트리 접근까지 모두 성공했다는 표시는 아니에요.

인증 보고서와 진단용 QID를 함께 읽으면서 인증 미시도, 로그인 실패, 로그인 후 접근 거부를 구분해 볼게요.

## 인증 스캔에서 추가로 수집하는 정보

비인증 스캔은 스캐너가 접근할 수 있는 서비스 응답을 바탕으로 검사해요. 인증 스캔은 제공된 계정으로 대상에 로그인해 내부 정보를 추가로 수집해요. Unix에서는 운영체제와 패키지 정보를, Windows에서는 권한이 허용하는 레지스트리·관리 공유·서비스 정보를 활용할 수 있어요.

인증 후 내부 정보가 수집되면 놓쳤던 항목이 나타나거나 기존 탐지의 판단이 달라질 수 있어요. 그래서 두 스캔의 취약점 개수와 수집 정보, 탐지 근거를 함께 비교해야 해요. 인증 성공만으로 다른 네트워크 위치에서도 접근할 수 있다고 판단하지는 않아요.

## 인증 기록과 실제 실행한 프로필을 함께 본다

이번 스캔에 사용한 옵션 프로필과 대상에 적용되는 인증 기록부터 대조해요. 프로필에서 필요한 인증 종류를 사용하도록 설정했는지, 인증 기록의 대상과 계정 정보가 맞는지 살펴봐요. 계정이 저장돼 있다는 사실만으로 해당 호스트의 인증에 사용됐다고 볼 수는 없어요.

Unix는 SSH 서비스와 접속 경로를, Windows는 선택한 인증 방식에 필요한 서비스와 통신 경로를 확인해요. SSH가 기본 포트가 아닌 곳에서 동작한다면 실제 포트와 검사 범위도 맞춰야 해요. 관리자가 자기 PC에서 로그인할 수 있어도 스캐너의 접속 경로와 조건은 다를 수 있어요.

포트·QID 범위와 자산별 최대 검사 시간도 함께 살펴봐요. 특히 `Test Authentication`은 인증 성공 여부를 확인하는 빠른 검사예요. 이 옵션을 사용하면 화면에 `Complete`가 선택돼 있어도 실제로는 인증 확인용 QID 목록을 검사해요. 인증 테스트가 성공했다면 예정한 취약점 평가를 별도로 실행하고 결과를 확인해야 해요.

## Passed는 보안 양호 판정이 아니다

VM/VMDR에서는 `Reports > New > Authentication Report`에서 인증 보고서를 생성할 수 있어요. 개별 스캔 결과의 `Appendix`도 함께 살펴봐요. 상태를 읽기 전에는 대상 호스트와 인증 종류, 결과가 어느 스캔 시점에 해당하는지부터 맞추고 실패 원인은 보고서의 `Cause`에서 확인해요.

Active Directory 인스턴스가 발견되면 OS 인증과 인스턴스별 인증을 따로 기록해요. 요약과 부록의 인증 성공 건수가 다를 때도 집계 단위부터 맞춰 봐요.

| 표시 | 의미 | 이후 확인 |
| --- | --- | --- |
| `Passed` | 해당 인증이 성공했다. | 필요한 정보 접근과 실제 평가 범위 |
| `Failed` | 해당 인증이 성공하지 못했다. | 실패 원인, 사용한 인증 기록과 계정 상태 |
| `Not Attempted` | 인증이 사용되지 않은 상태다. | 대상·프로필·서비스 조건과 보고서 이력 |
| `Passed*` | 인증은 성공했지만 계정 권한이 부족하다. 문서상 PC에 한정된 표시다. | 해당 검사에서 요구하는 권한과 접근 제한 |

여기서 PC는 Policy Compliance, PA는 Policy Audit의 약어예요. [Qualys의 제품 명칭 안내](https://docs.qualys.com/en/vm/qweb-all-api/get_started/get_started.htm)는 두 이름을 구분해 설명해요. 인증 보고서 문서의 `Passed*`는 PC에 한정된 표시이고 권한 부족 안내의 PA 검사 설명에도 등장해요. 모든 VM 화면의 공통 상태는 아니므로 별표 하나보다 해당 검사에서 실제로 거부된 파일·레지스트리 접근을 살펴봐요.

`Not Attempted`도 현재 프로필의 설정만으로 설명되지 않을 수 있어요. 보고서에는 인증한 이력이 없거나 호스트 스캔 데이터가 삭제된 경우도 반영될 수 있거든요. 이번 스캔의 미시도 원인은 해당 실행 결과와 설정을 함께 확인하며 좁혀 가요.

`Additional Host Info`를 포함하면 `Last Auth`와 `Last Success`를 볼 수 있어요. `Last Auth`는 인증을 사용한 마지막 검사에서 상태가 Passed 또는 Failed로 갱신된 시각이고, `Last Success`는 마지막 인증 성공 시각이에요. `Last Success`가 `N/A`면 인증을 켠 검사에서 성공한 이력이 없다는 뜻이에요. 두 값을 비교하면 과거의 성공을 이번 결과로 잘못 읽는 일을 피할 수 있어요.

인증 이력은 Host ID에 연결돼 인증 기록을 수정·삭제해도 과거 결과가 남아요. 인증 기록의 요약이 `Failing`인데 현재 자산에는 실패가 없다면 과거에 연결됐던 자산의 실패 이력도 살펴봐요.

## 로그인 이후의 접근 거부는 QID로 확인한다

QID는 Qualys의 검사 항목 식별자예요. 인증 관련 QID 중에는 취약점이 아니라 검사 상태를 설명하는 `Information Gathered` 항목도 있어요. 인증 성공을 알리는 항목이 있더라도 필요한 파일과 레지스트리를 모두 읽었다는 뜻은 아니에요.

| 대상 | QID | 확인할 내용 |
| --- | --- | --- |
| Unix | `38307` | 인증 성공 시 사용한 인증 방법 |
| Unix | `105053` | 인증 실패 |
| Unix | `105297` | 인증 미시도 |
| Windows | `70053` | 사용자가 제공한 자격 증명으로 인증 성공 |
| Windows | `105015` | 인증 기록의 자격 증명으로 로그인 시도 후 실패 |
| Windows | `105296` | 인증을 사용하도록 설정했지만 대상이 인증 기록에 포함되지 않아 미시도 |
| Windows | `90399` | 공유에는 접근했지만 Results에 표시된 파일은 읽지 못함 |
| Windows | `90195` | 레지스트리 파이프에는 접근했지만 Results에 표시된 키는 읽지 못함 |

예를 들어 같은 Windows 호스트의 한 스캔에 `70053`과 `90399`가 함께 있다면 로그인에는 성공했어도 일부 파일을 읽지 못한 상황이에요. `90399`의 `Results`에서 해당 파일을 찾아 어떤 검사의 근거가 빠졌는지 조사할 수 있어요.

특정 QID가 보이지 않으면 보고서에서 정보 수집 항목을 표시하는지, 해당 검사가 범위에 포함됐는지부터 조사해요. 같은 자산·스캔 시점의 결과를 비교하기 전에는 문제가 없다고 확정할 수 없어요. 인증 진단용 정보 수집 항목은 취약점 건수와 구분해 보고해요.

## 권한 부족과 인증 실패는 결과가 다르다

VM 취약점 스캔은 로그인에 성공한 뒤 권한이 부족하더라도 읽을 수 있는 정보로 평가를 진행할 수 있어요. 이 경우 일부 검사가 빠지거나 정보 부족으로 미탐·오탐이 생길 수 있어요. 로그인 실패 시에는 일반적으로 비인증 스캔을 수행해요.

Windows 인증 기록의 `SMB signing required` 또는 최소 SMB 버전 요구사항을 대상이 충족하지 못하면 인증 실패와 함께 호스트 스캔도 수행되지 않아요. 작업 종료 상태와 인증 결과를 읽을 때 실제 평가 여부까지 확인해요.

컴플라이언스 검사는 다르게 살펴봐야 해요. 공식 문서는 인증에 실패하면 평가 데이터를 수집하지 못한다고 설명해요. VM에서 비인증 결과를 얻었다는 경험을 컴플라이언스 검사에 그대로 적용하지 말고 제품과 검사 종류부터 확인해요.

권한 부족이 확인되면 대상 운영체제의 요구사항과 실제 접근 거부 대상을 대조해요. Windows VM/VMDR 문서는 정확한 평가를 위해 관리자 권한을 권장해요. 더 낮은 권한으로도 검사할 수 있지만 검사 범위와 결과의 완전성은 줄어들어요. 필요한 권한은 담당자와 검토하고 조직 정책상 허용하지 않는 범위는 미확인 항목으로 남겨요.

Unix VM은 root 권한이 일률적인 필수 조건은 아니에요. 다만 운영체제·패키지 확인 등 검사에 필요한 명령을 실행하고 정보를 읽을 수 있어야 해요. `Attempt least privilege for Unix` 옵션은 VM 스캔에서 인증 기록의 root 권한 위임 정보를 스캐너에 전달하지 않도록 해요. 컴플라이언스 검사에는 영향을 주지 않으며 필요한 권한을 자동으로 부여하거나 모든 검사의 완전성을 보장하는 기능도 아니에요.

## 재검사에서 인증 상태와 접근 거부를 확인한다

처음 확인할 때는 허가된 실습 자산 한두 대에서 시작해요. 점검 목적과 전용 계정, 사용할 프로필, 접속 경로와 작업 시간을 정해 둬요. 운영 계정을 잠그거나 파일 권한을 일부러 바꾸지 않아도 기존 결과의 상태와 원인을 읽는 연습부터 할 수 있어요.

인증 미시도라면 대상과 인증 설정·접속 경로를, 인증 실패라면 Cause와 계정 상태를 확인해요. 로그인 이후 접근 거부라면 필요한 권한과 서비스 조건을 조사해요. 계정과 네트워크 정책은 승인된 범위에서 변경하며 인증 문제를 해결하려고 잠금 정책을 끄거나 관리 포트를 넓게 개방하지 않아요.

조치 후에는 같은 대상과 평가 목적을 유지해 새 스캔을 확인해요. 인증이 성공했는지에 더해 이전에 읽지 못한 정보가 수집됐는지, 접근 거부가 남았는지, 관련 취약점의 탐지 근거가 어떻게 달라졌는지 살펴봐요. 새 항목이 늘었다면 보안 상태의 변화와 검사 범위의 회복을 구분해 해석해요.

보고서에서 인증 복구와 취약점 조치를 구별하려면 대상·스캔 시각·인증 상태·남은 접근 제한이 필요해요. 중요 자산의 정보를 여전히 읽지 못한다면 미확인 범위와 후속 담당자를 명시해요. 화면이나 결과를 공유하기 전에는 자격 증명과 불필요한 내부 식별 정보를 가려요.
