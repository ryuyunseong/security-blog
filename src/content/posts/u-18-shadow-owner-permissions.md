`/etc/shadow`의 권한이 `0600`이면 일반 사용자는 내용을 읽을 수 없어요. 그런데 2026년 주통기 U-18의 기준은 `0400` 이하라서 소유자에게 쓰기 권한이 남아 있는 `0600`도 기준과 차이가 있어요. ‘일반 사용자에게 안 보인다’와 ‘점검 항목의 권한 조건을 충족한다’를 구별해서 살펴볼게요.

## 0400에서 허용하는 비트

2026 KISA 상세가이드 44쪽의 U-18은 중요도 ‘상’이에요. 대상은 Solaris·Linux·AIX·HP-UX 등이며 shadow 파일의 소유자가 root이고 권한이 `400` 이하이면 양호, 소유자가 root가 아니거나 권한 조건을 벗어나면 취약으로 판단해요. 여기서 권한 표시는 8진수예요.

`0400`은 소유자 읽기만 허용해요. `0600`에는 소유자 쓰기 `0200`이, `0440`에는 그룹 읽기 `0040`이 더해져 있어요. [앞서 본 passwd 파일의 U-16](../u-16-passwd-owner-permissions/)과 달리 이번 기준은 그룹 읽기도 허용하지 않아요.

[[diagram]]

‘이하’를 정수 크기 비교로 구현하면 문제가 생겨요. `0004`는 숫자로는 `0400`보다 작지만 기타 사용자 읽기를 허용하거든요. 기준이 허용하지 않는 **권한이 켜졌는지** 비트로 비교해야 해요. 일반 권한 비트만 놓고 보면 `0000`도 허용 밖 비트가 없지만 이 결과가 인증 도구의 정상 동작까지 보장하지는 않아요.

## 파일 내용 대신 소유자와 접근 권한 수집하기

Linux의 [shadow(5) 문서](https://man7.org/linux/man-pages/man5/shadow.5.html)는 일반 사용자가 이 파일을 읽지 못하도록 설명해요. 비밀번호 관련 필드가 담겨 있으므로 권한 점검 보고서에 해시나 파일 전체를 붙일 필요는 없어요. 파일 경로, 숫자 UID·GID, 모드와 ACL 등 접근 조건을 수집하면 돼요.

가이드가 제시하는 조치 경로도 운영체제마다 달라요.

| 운영체제 | 가이드의 경로 | 수집할 때 구분할 점 |
| --- | --- | --- |
| Solaris·Linux | `/etc/shadow` | 파일 소유자와 일반 권한, ACL |
| AIX | `/etc/security/passwd` | Linux 경로로 대체하지 않기 |
| HP-UX | `/tcb/files/auth/` | 디렉터리 및 그 안의 인증 자료 구조 |

실제 설정을 바꾸기 전에는 해당 제품의 인증·계정 관리 도구와 패키지 권한 정책을 함께 살펴봐요. 가이드의 모드 예시를 다른 운영체제의 모든 인증 파일에 일괄 적용하는 방식은 피해요. ACL이나 상위 디렉터리의 교체 권한으로 접근 범위가 달라지는지도 별도로 검토해요.

## 가상 속성 아홉 건 비교

실습은 Python 3.9 이상과 표준 기능만 사용해요. ZIP을 빈 폴더에 풀고 `u18_shadow_mode.py`가 있는 폴더에서 `python -I -B -X utf8 u18_shadow_mode.py`를 실행해요. Bash에서는 `python3`를 써도 되며 관리자 권한은 필요하지 않아요.

입력은 코드의 `CASES`에 들어 있어요. `/etc/shadow`나 `/lab` 파일을 만들거나 열지 않고 실제 UID·권한도 조회하지 않아요. 그래서 Windows에서도 같은 비트 계산을 실행할 수 있으며 종료 뒤 지울 실습 파일이나 계정도 없어요.

[[download]]

```python
CASES = (
    ("기준 권한", 0, 0o400, "조건 충족"),
    ("소유자 쓰기", 0, 0o600, "권한 초과"),
    ("그룹 읽기", 0, 0o440, "권한 초과"),
    ("기타 읽기", 0, 0o404, "권한 초과"),
    ("숫자가 작은 모드", 0, 0o004, "권한 초과"),
    ("일반 권한 없음", 0, 0o000, "조건 충족"),
    ("다른 소유자", 1001, 0o400, "소유자 불일치"),
    ("특수 비트", 0, 0o4400, "범위 밖"),
    ("소유자 미수집", None, 0o400, "미수집"),
)


def compare(uid, mode):
    # 실제 파일을 조회하지 않고 전달받은 가상 속성만 비교한다.
    if uid is None or mode is None:
        return "미수집", None
    if type(uid) is not int or uid < 0:
        raise ValueError("UID는 0 이상의 정수여야 한다")
    if type(mode) is not int or not 0 <= mode <= 0o7777:
        raise ValueError("모드 범위 오류")
    if mode & 0o7000:
        return "범위 밖", None
    extra = mode & (~0o400 & 0o777)
    if uid != 0:
        return "소유자 불일치", extra
    return ("권한 초과" if extra else "조건 충족"), extra


def main():
    for label, uid, mode, expected in CASES:
        state, extra = compare(uid, mode)
        if state != expected:
            raise AssertionError(f"{label}: {state!r} != {expected!r}")
        bits = "비교 안 함" if extra is None else f"{extra:03o}"
        print(f"{label}: UID={uid}, 모드={mode:04o}, 추가 비트={bits}, {state}")
    print(f"가상 속성 {len(CASES)}건의 기대 상태 일치")


if __name__ == "__main__":
    main()
```

`CASES`의 각 항목은 이름, UID, 모드, 기대 상태 순서예요. `compare()`는 값 누락을 먼저 걸러 낸 뒤 정수 형식과 범위를 검사해요. 이번 예제에서는 일반 권한만 비교하므로 특수 비트 `07000` 중 하나라도 있으면 ‘범위 밖’으로 분류해요.

`extra = mode & (~0o400 & 0o777)`에서 `~0o400`은 허용 비트를 반전해요. Python의 정수 반전은 음수가 되므로 `0o777`과 한 번 더 AND 연산해 일반 권한 9비트로 범위를 제한해요. 그러면 최종 `extra`에는 허용하지 않은 권한만 남아요.

예를 들어 `0600`을 넣으면 소유자 읽기 `0400`은 제거되고 쓰기 `0200`이 남아요. `extra`가 0이 아니므로 ‘권한 초과’가 반환돼요. UID가 0이 아니면 그보다 먼저 ‘소유자 불일치’를 반환하는데, 이 경우에도 추가 비트 값을 출력해 두 조건을 함께 볼 수 있게 했어요.

[[run:1]]

‘기준 권한’은 추가 비트가 `000`, ‘소유자 쓰기’는 `200`, ‘그룹 읽기’는 `040`이에요. 출력의 모드와 추가 비트는 모두 8진수이므로 `200`을 십진수 200으로 읽지 않아요. ‘숫자가 작은 모드’에서도 `004`가 남아 기타 읽기를 찾아냈어요.

특수 비트와 UID 누락 사례에 표시된 ‘비교 안 함’은 추가 비트를 계산하지 않았다는 뜻이에요. 이 상태를 `000`과 같은 결과로 처리하지는 않아요. 현재 코드에서는 소유자와 권한 조건을 동시에 벗어난 입력에도 소유자 불일치가 먼저 표시되므로 상태 이름 하나만 보고 권한을 검토에서 제외해서는 안 돼요.

마지막 줄과 프로세스 종료 코드 0은 **가상 입력 아홉 건의 상태가 기대값과 일치했다는 뜻**이에요. 실제 파일의 양호·취약 판정은 수집한 소유자·권한과 해당 시스템의 접근 조건을 대조해 남겨요. 형식 오류는 `ValueError`, 기대 상태 불일치는 `AssertionError`로 실행을 중단하며 빈 성공 결과로 감추지 않아요.
