자산은 목록에 있는데 취약점 결과가 비어 있다. 결과가 없다고 양호로 판단하면 수집 누락이나 오래된 평가를 놓칠 수 있다.

Cloud Agent와 Scanner Appliance 공식 문서에서 통신 상태, VM 활성화, 스캔 범위, 평가 시점을 확인하는 순서를 정리했다. 고객 환경이나 운영 스캔 자료는 사용하지 않았다.

## 대상 포함, 통신, 평가, 결과 반영을 나눠 확인한다

수집 경로는 자산별로 정한다. 에이전트를 설치할 수 있는 서버나 이동하는 노트북은 호스트 내부 수집을 활용할 수 있다. 에이전트 설치가 어려운 네트워크 장비는 스캐너의 위치와 지원되는 검사 방식을 먼저 확인한다. 각 자산에서 필요한 정보를 어떤 경로로 얻을지 정해야 누락된 구간을 찾을 수 있다.

| 확인 단계 | Cloud Agent | Scanner Appliance |
| --- | --- | --- |
| 대상 포함 | 해당 호스트에 설치되고 올바른 구독에 연결됐는가 | 허가된 대상이 이번 스캔 범위에 포함됐는가 |
| 통신 | 호스트에서 지정 플랫폼으로 연결되는가 | 플랫폼 관리 통신과 대상까지의 검사 통신이 각각 가능한가 |
| 평가 조건 | VM 활성화와 적용된 구성 프로필이 맞는가 | 포트·QID·인증 옵션이 의도한 검사에 맞는가 |
| 결과 반영 | 최근 접속 시각과 별개로 새 평가 결과가 반영됐는가 | 검사·미검사 호스트와 인증 실패를 구분했는가 |

설치 여부나 최근 접속 시각 하나로 전체 수집 상태를 판단하지 않는다. 자산 목록과 담당자 정보를 먼저 맞춘 뒤, 어느 단계에서 결과가 이어지지 않았는지 좁혀 간다.

## 에이전트의 VM 활성화와 평가 시점을 확인한다

Windows용 Cloud Agent를 설치하려면 대상 호스트의 관리자 권한과 지정 플랫폼으로의 HTTPS 443 연결이 필요하다. 접속해야 할 주소는 자신의 구독에서 Help > About으로 확인한다. 지원 운영체제와 필요한 자원은 배포할 에이전트 버전과 앱의 요구사항에 맞춰 확인한다.

설치 후에는 취약점 관리에 사용할 VM이 해당 에이전트에서 활성화됐는지 살핀다. 앱을 활성화하지 않은 에이전트는 운영체제·주소·설치 소프트웨어 등의 인벤토리 정보만 전송한다. 자산은 보이는데 취약점 결과가 없다면 구독의 VM 제공 범위와 에이전트의 활성화 상태부터 대조한다.

그다음은 적용된 구성 프로필이다. Data Collection Interval은 이전 수집이 끝난 뒤 다음 수집을 시작하기까지의 간격이며, Scan Delay와 Scan Randomize도 시작 시점에 영향을 준다. 플랫폼 접속 시각과 새 VM 평가의 완료·반영 시각을 구분하고, 기대한 주기와 실제 결과 시점을 비교한다.

프로필을 바꾸기 전에는 자산 하나의 적용 프로필, 에이전트 서비스 상태, 통신 오류와 평가 시점을 확인한다. 주기 조정이나 프로필 재적용이 필요하면 대상 범위를 제한하고, 변경 후 새 결과가 들어오는지 살핀다.

## 스캐너의 관리 통신과 검사 통신을 구분한다

Scanner Appliance는 Qualys 플랫폼으로 HTTPS 443 아웃바운드 통신을 수행한다. 작업과 업데이트를 받아오고 상태와 결과를 전달하는 경로다. DNS, 라우팅, 방화벽과 프록시 설정이 이 통신을 허용해야 하며, 필요한 플랫폼 주소는 구독의 Help > About에서 확인한다.

플랫폼 관리 통신이 정상이어도 검사할 서버까지의 경로는 막혀 있을 수 있다. 스캐너가 플랫폼에 표시된다는 사실은 대상 포트에 도달했다는 증거가 아니다. 대상에 접근했더라도 결과 전송에 문제가 생기면 화면에 최신 결과가 나타나지 않을 수 있으므로 두 구간을 따로 조사한다.

스캔 설정에서는 대상 주소·태그, 제외 목록, 선택한 스캐너와 옵션 프로필을 확인한다. 포트나 QID가 제한되어 있다면 결과도 그 범위 안에서 해석한다. 인증 스캔에는 대상에 맞는 인증 기록과 프로필의 인증 옵션이 모두 필요하며, 설정 여부와 인증 성공 여부는 별도로 확인한다.

완료된 스캔에서는 Appendix의 검사·미검사 호스트와 인증 실패 목록을 먼저 읽는다. 인증 문제는 Authentication Report로 좁힌다. 제외되거나 응답하지 않아 검사되지 않은 대상은 취약점이 없는 대상과 구분해 기록한다.

## Remote Detection은 검사 위치까지 설명한다

Cloud Agent는 호스트 내부 정보 수집에 더해 Remote Detection을 지원한다. 설정에 따라 가벼운 스캐너 바이너리를 내려받아 TLS 검사, 배너 수집, 패킷 기반 탐지를 수행한다. 이 기능의 검사 대상은 에이전트가 설치된 자기 호스트다.

자기 호스트에서 수행한 검사와 사외 또는 다른 네트워크 구간에서 접근한 검사는 관찰 조건이 다르다. Remote Detection 결과만으로 외부 접근 가능성을 확인했다고 볼 수는 없다. 외부 노출을 판단하려면 허가된 위치에서 통신 경로와 서비스 응답을 별도로 확인한다.

적용 전에는 해당 환경의 기능 지원 여부, 활성화 상태, 수집 간격과 제외 포트를 확인한다. 에이전트 버전이나 구독에 따라 사용할 수 있는 조건을 대조해야 한다. 다른 장비를 대신 검사하는 범용 네트워크 스캐너로 이해하지 않는다.

## 같은 서버가 두 번 보이면 식별 방식부터 확인한다

에이전트와 네트워크 스캔을 함께 쓰면 같은 장비의 결과가 별도 자산으로 표시될 수 있다. Asset Tracking & Data Merging은 병합하지 않는 방식, 스캔 방식별 병합, 하나의 자산으로 통합하는 방식 등을 제공한다. 센서 두 개의 결과가 자동으로 한 자산에 모인다고 가정하지 말고 실제 병합 설정을 확인한다.

주소가 바뀌는 장비를 IP만으로 비교하면 여러 자산으로 나뉠 수 있다. 복제 장비에 같은 자산 UUID가 남아 있으면 서로 다른 장비가 하나로 합쳐질 수도 있다. 자산 이름만 보고 중복 항목을 삭제하지 말고, 식별자·주소·수집 출처와 실제 장비의 대응 관계를 확인한다.

| 식별자 | 용도와 확인할 조건 |
| --- | --- |
| Agentless Tracking Identifier | 인증 스캔에서 호스트 ID로 자산을 추적한다. Unix는 지정 위치 아래에 식별자 파일을 만들고, Windows는 레지스트리에 저장한다. 구독 설정과 인증 기록의 활성화 조건을 확인한다. |
| Agent Correlation Identifier | 에이전트 결과와 네트워크 취약점 결과를 연계한다. Agent Scan Merge 프로필에 지정한 포트를 스캐너가 검사할 수 있어야 하며, 포트 충돌과 프로필 적용 범위를 확인한다. |

Agentless Tracking은 대상에 식별자를 기록하는 기능이다. 도입 시에는 담당자 승인과 변경 절차에 따라 저장 위치와 적용 범위를 검토한다. Agent Correlation Identifier를 수집할 때도 대상 호스트의 프로필, 스캐너 옵션의 포트 범위와 허용된 통신 경로를 함께 맞춘다.

병합은 결과를 모아 보는 방법이며 빠진 검사를 대신 수행하지는 않는다. 병합을 해제하면 기존 에이전트 자산에 합쳐졌던 일부 스캐너 전용 결과가 더 이상 갱신되지 않을 수 있다. 표시 개수가 달라졌다면 탐지 상태를 판단하기 전에 설정 변경과 식별 기준의 영향을 확인한다.

## 결과가 다르면 수집 조건을 맞춰 비교한다

같은 서버의 취약점 개수가 센서마다 다르다고 바로 오탐으로 판단하지 않는다. 수집 시각, 검사 범위, 인증 결과와 표시 필터를 맞춘 뒤 실제 탐지 근거를 비교한다. 의심 항목은 해당 호스트 QID의 Results를 읽고 제품·설정 상태와 대조한다.

자산 병합과 탐지 항목의 중복도 구분한다. 같은 QID라도 포트·프로토콜·FQDN 등이 다르면 서로 다른 탐지 항목일 수 있다. 서버 이름과 QID만으로 결과를 합치면 서로 다른 서비스의 정보를 잃을 수 있다.

| 설명용 상황 | 바로 내리면 안 되는 결론 | 다음에 확인할 내용 |
| --- | --- | --- |
| 에이전트 자산에 소프트웨어 목록만 보인다 | 취약점이 없는 서버다 | VM 활성화, 적용 프로필, 평가 결과 시점 |
| 스캐너는 정상인데 대상 결과가 비어 있다 | 대상이 안전하거나 꺼져 있다 | 대상 포함·제외 여부, 검사 경로, 미검사 사유 |
| 같은 장비가 에이전트·IP 자산으로 나뉜다 | 하나가 불필요하므로 삭제한다 | 추적 식별자, 병합 설정, 실제 장비와의 대응 관계 |
| 조치 후 한 센서의 결과만 바뀐다 | 모든 관점에서 조치가 끝났다 | 각 센서의 수집 시점, 검사 조건과 탐지 근거 |

첫 확인은 허가된 실습 자산 한두 대로 시작한다. 동일한 자산이 각 수집 경로에서 어떻게 나타나는지, 검사가 빠졌을 때 어떤 사유가 남는지 확인하면 누락을 구분하는 데 도움이 된다.

## 수집 보완 작업과 취약점 조치를 따로 기록한다

후속 작업은 확인한 원인에 맞춰 정한다. 에이전트의 활성화나 통신 문제, 스캐너의 검사 경로와 범위, 자산 식별과 병합 조건을 각각 보완한다. 이런 작업은 수집 누락을 해소한 것이므로 취약점 자체를 수정한 작업과 따로 기록한다.

보완 순서는 자산의 중요도와 노출 범위를 함께 고려한다. 외부 공개 업무 서버처럼 영향이 큰 자산의 결과가 오래됐거나 검사가 빠졌다면 우선 확인할 필요가 있다. 확인하지 못한 구간은 양호로 처리하지 않고 담당자와 보완 일정을 정한다.

작업 후에는 새 평가 결과가 들어왔는지 확인하고 같은 자산·서비스·검사 조건으로 비교한다. 보고서에는 수집 출처, 결과 시점, 누락 사유, 보완 작업과 재확인 결과를 적는다. 아직 확인하지 못한 대상과 그 사유도 함께 기록한다.
