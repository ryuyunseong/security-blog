자산 목록과 취약점 결과는 갱신 시점이 다를 수 있어요. 목록에는 호스트가 보이는데 평가 결과가 없다면 Cloud Agent의 VM 활성화 상태나 스캐너의 검사·미검사 내역부터 살펴봐요.

## 대상 포함, 통신, 평가, 결과 반영을 나눠 확인한다

수집 경로는 자산별로 정해요. 에이전트를 설치할 수 있는 서버나 이동하는 노트북은 호스트 내부 수집을 활용할 수 있어요. 에이전트 설치가 어려운 네트워크 장비라면 스캐너의 위치와 지원되는 검사 방식을 먼저 살펴봐요. 각 자산에서 필요한 정보를 어떤 경로로 얻을지 정해야 누락된 구간을 찾을 수 있어요.

| 확인 단계 | Cloud Agent | Scanner Appliance |
| --- | --- | --- |
| 대상 포함 | 해당 호스트에 설치되고 올바른 구독에 연결됐는가 | 허가된 대상이 이번 스캔 범위에 포함됐는가 |
| 통신 | 호스트에서 지정 플랫폼으로 연결되는가 | 플랫폼 관리 통신과 대상까지의 검사 통신이 각각 가능한가 |
| 평가 조건 | VM 활성화와 적용된 구성 프로필이 맞는가 | 포트·QID·인증 옵션이 의도한 검사에 맞는가 |
| 결과 반영 | 최근 접속 시각과 별개로 새 평가 결과가 반영됐는가 | 검사·미검사 호스트와 인증 실패를 구분했는가 |

담당자와 대상 자산을 정한 뒤 표의 순서대로 통신과 평가가 어느 단계까지 진행됐는지 살펴봐요. 설치 여부와 최근 접속 시각만으로는 최신 평가 결과가 반영됐는지 알 수 없어요.

## 에이전트의 VM 활성화와 평가 시점을 확인한다

Windows용 Cloud Agent를 설치하려면 대상 호스트의 관리자 권한과 지정 플랫폼으로의 HTTPS 443 연결이 필요해요. 접속해야 할 주소는 자신의 구독에서 Help > About으로 확인해요. 지원 운영체제와 필요한 자원도 배포할 에이전트 버전과 앱의 요구사항에 맞춰 살펴봐요.

설치 후에는 취약점 관리에 사용할 VM이 해당 에이전트에서 활성화됐는지 살펴봐요. 앱을 활성화하지 않은 에이전트는 운영체제·주소·설치 소프트웨어 등의 인벤토리 정보만 전송해요. 자산은 보이는데 취약점 결과가 없다면 구독의 VM 제공 범위와 에이전트의 활성화 상태부터 대조해요.

그다음으로 볼 항목은 적용된 구성 프로필이에요. Data Collection Interval은 이전 수집이 끝난 뒤 다음 수집을 시작하기까지의 간격이고 Scan Delay와 Scan Randomize도 시작 시점에 영향을 줘요. 플랫폼 접속 시각과 새 VM 평가의 완료·반영 시각을 구분해 기대한 주기와 실제 결과 시점을 비교해요.

프로필을 바꾸기 전에는 자산 하나의 적용 프로필, 에이전트 서비스 상태, 통신 오류와 평가 시점을 살펴봐요. 주기 조정이나 프로필 재적용이 필요하면 대상 범위를 제한하고 변경 후 새 결과가 들어오는지 확인해요.

## 스캐너의 관리 통신과 검사 통신을 구분한다

Scanner Appliance는 Qualys 플랫폼으로 HTTPS 443 아웃바운드 통신을 수행해요. 작업과 업데이트를 받아오고 상태와 결과를 전달하는 경로예요. DNS, 라우팅, 방화벽과 프록시 설정이 이 통신을 허용해야 하며 필요한 플랫폼 주소는 구독의 Help > About에서 확인해요.

스캐너가 플랫폼에 표시돼도 검사 대상 서버까지 통신된 것은 아닐 수 있어요. 대상에 접근했지만 결과 전송이 막혀 최신 결과가 보이지 않는 경우도 있으므로 플랫폼 관리 통신과 대상 검사 통신을 나눠 조사해야 해요.

스캔 설정에서는 대상 주소·태그, 제외 목록, 선택한 스캐너와 옵션 프로필을 살펴봐요. 포트나 QID가 제한되어 있다면 결과도 그 범위 안에서 해석해요. 인증 스캔에는 대상에 맞는 인증 기록과 프로필의 인증 옵션이 모두 필요하며 설정 여부와 인증 성공 여부는 별도로 확인해요.

완료된 스캔에서는 Appendix의 검사·미검사 호스트와 인증 실패 목록부터 읽어 봐요. 인증 문제는 Authentication Report로 좁혀요. 제외되거나 응답하지 않아 검사되지 않은 대상은 취약점이 없는 대상과 구분해 기록해요.

## Remote Detection은 검사 위치까지 설명한다

Cloud Agent는 호스트 내부 정보 수집에 더해 Remote Detection을 지원해요. 설정에 따라 가벼운 스캐너 바이너리를 내려받아 TLS 검사, 배너 수집, 패킷 기반 탐지를 수행해요. 이 기능의 검사 대상은 에이전트가 설치된 자기 호스트예요.

자기 호스트에서 수행한 검사와 사외 또는 다른 네트워크 구간에서 접근한 검사는 관찰 조건이 달라요. Remote Detection 결과만으로 외부 접근 가능성을 확인했다고 볼 수는 없어요. 외부 노출을 판단하려면 허가된 위치에서 통신 경로와 서비스 응답을 별도로 확인해요.

적용 전에는 해당 환경의 기능 지원 여부, 활성화 상태, 수집 간격과 제외 포트를 살펴봐요. 에이전트 버전이나 구독에 따라 사용할 수 있는 조건을 대조해야 해요. 다른 장비를 대신 검사하는 범용 네트워크 스캐너로 이해하지는 않아요.

## 같은 서버가 두 번 보이면 식별 방식부터 확인한다

에이전트와 네트워크 스캔을 함께 쓰면 같은 장비의 결과가 별도 자산으로 표시될 수 있어요. Asset Tracking & Data Merging은 병합하지 않는 방식, 스캔 방식별 병합, 하나의 자산으로 통합하는 방식 등을 제공해요. 센서 두 개의 결과가 자동으로 한 자산에 모인다고 가정하지 말고 실제 병합 설정을 확인해요.

주소가 바뀌는 장비를 IP만으로 비교하면 여러 자산으로 나뉠 수 있어요. 반대로 복제 장비에 같은 자산 UUID가 남아 있으면 서로 다른 장비가 하나로 합쳐질 수도 있어요. 자산 이름만 보고 중복 항목을 삭제하지 말고 식별자·주소·수집 출처와 실제 장비의 대응 관계를 살펴봐요.

| 식별자 | 용도와 확인할 조건 |
| --- | --- |
| Agentless Tracking Identifier | 인증 스캔에서 호스트 ID로 자산을 추적한다. Unix는 지정 위치 아래에 식별자 파일을 만들고, Windows는 레지스트리에 저장한다. 구독 설정과 인증 기록의 활성화 조건을 확인한다. |
| Agent Correlation Identifier | 에이전트 결과와 네트워크 취약점 결과를 연계한다. Agent Scan Merge 프로필에 지정한 포트를 스캐너가 검사할 수 있어야 하며, 포트 충돌과 프로필 적용 범위를 확인한다. |

Agentless Tracking은 대상에 식별자를 기록하는 기능이에요. 도입 시에는 담당자 승인과 변경 절차에 따라 저장 위치와 적용 범위를 검토해요. Agent Correlation Identifier를 수집할 때도 대상 호스트의 프로필, 스캐너 옵션의 포트 범위와 허용된 통신 경로를 함께 맞춰요.

병합은 결과를 모아 보는 방법이며 빠진 검사를 대신 수행하지는 않아요. 병합을 해제하면 기존 에이전트 자산에 합쳐졌던 일부 스캐너 전용 결과가 더 이상 갱신되지 않을 수 있어요. 표시 개수가 달라졌다면 병합 설정이나 자산 식별 기준이 바뀌었는지 먼저 살펴보고 그 영향을 구분한 뒤 탐지 상태를 해석해요.

## 결과가 다르면 수집 조건을 맞춰 비교한다

같은 서버의 취약점 개수가 센서마다 다르다고 바로 오탐으로 판단하지는 않아요. 수집 시각, 검사 범위, 인증 결과와 표시 필터를 맞춘 뒤 실제 탐지 근거를 비교해요. 의심 항목은 해당 호스트 QID의 Results를 읽고 제품·설정 상태와 대조해요.

자산 병합과 탐지 항목의 중복도 구분해요. 같은 QID라도 포트·프로토콜·FQDN 등이 다르면 서로 다른 탐지 항목일 수 있어요. 서버 이름과 QID만으로 결과를 합치면 서로 다른 서비스의 정보를 잃을 수 있어요.

| 설명용 상황 | 바로 내리면 안 되는 결론 | 다음에 확인할 내용 |
| --- | --- | --- |
| 에이전트 자산에 소프트웨어 목록만 보인다 | 취약점이 없는 서버다 | VM 활성화, 적용 프로필, 평가 결과 시점 |
| 스캐너는 정상인데 대상 결과가 비어 있다 | 대상이 안전하거나 꺼져 있다 | 대상 포함·제외 여부, 검사 경로, 미검사 사유 |
| 같은 장비가 에이전트·IP 자산으로 나뉜다 | 하나가 불필요하므로 삭제한다 | 추적 식별자, 병합 설정, 실제 장비와의 대응 관계 |
| 조치 후 한 센서의 결과만 바뀐다 | 모든 관점에서 조치가 끝났다 | 각 센서의 수집 시점, 검사 조건과 탐지 근거 |

실습에서는 허가된 자산 한두 대를 골라 각 센서의 자산 식별 정보와 검사 내역을 나란히 놓아 봐요. 미검사 사유와 결과 갱신 시점을 대조하는 데 집중하면 돼요.

## 수집 보완 작업과 취약점 조치를 따로 기록한다

후속 작업은 누락 원인에 맞춰 정해요. 에이전트 활성화·통신 문제, 스캐너의 검사 경로·범위, 자산 식별·병합 조건을 각각 보완해요. 이 작업으로 수집이 복구됐더라도 취약점을 조치한 것으로 기록하지는 않아요.

보완 순서는 자산의 중요도와 노출 범위를 함께 고려해요. 외부 공개 업무 서버처럼 영향이 큰 자산의 결과가 오래됐거나 검사가 빠졌다면 우선 확인할 필요가 있어요. 확인하지 못한 구간은 양호로 처리하지 않고 담당자와 보완 일정을 정해요.

새 결과가 들어오면 같은 자산·서비스·검사 조건으로 전후를 비교해요. 보고서에는 수집 출처와 시점, 누락 원인, 수행한 작업을 적고 결과를 얻지 못한 대상에는 남은 사유와 보완 일정을 남겨요.
